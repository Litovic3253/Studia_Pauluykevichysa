# Mochi Desktop — приложение-панель управления (дизайн)

Дата: 2026-09-24

## Контекст

Есть работающий Telegram-бот «Mochi» (`bot.py`, aiogram) для приёма и ведения
заказов на 3D-печать, хранящий всё в SQLite (`orders.db` через `db.py`):
заказы, статусы, настройки цен (материалы, ставка часа, реверс-инжиниринг).

Владелец хочет Windows-приложение, из которого можно:
- видеть и редактировать все заказы и клиентов;
- полностью управлять ценами/настройками (без команд в Telegram);
- видеть статистику.

Бот при этом продолжает работать и принимать заказы от клиентов в Telegram —
приложение это админ-панель поверх той же базы, не замена бота.

## Решение

Два независимых процесса на одной машине, общающихся только через общий
файл SQLite `orders.db`:

- **`bot.py`** — работает без изменений бизнес-логики.
- **`app/`** — новое Flet-приложение (Python), импортирует `db.py` и функции
  расчёта цены напрямую. Никакого HTTP между ботом и приложением, никакого
  дублирования логики на другом языке.

Стек: **Python + Flet**. Даёт нативное окно Windows, современные виджеты
(таблицы, карточки, вкладки) из коробки, и позволяет переиспользовать весь
существующий Python-код без переписывания. Альтернативы (CustomTkinter —
проще, но менее современный вид и больше ручной вёрстки таблиц; локальный
веб-сервер + pywebview — лишний процесс ради веб-страницы в окне) были
рассмотрены и отклонены.

## Данные

### Совместный доступ бота и приложения к SQLite

Включаем `PRAGMA journal_mode=WAL` в `db.py` (в `init()`). WAL позволяет
одному writer и множеству readers работать одновременно без блокировок,
которые ловит текущий `journal_mode=DELETE` при конкурентном доступе.
Изменение безопасно для уже работающего бота (WAL — это только режим
журнала, схема не меняется).

### Новая таблица `customers`

```sql
CREATE TABLE customers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    contact TEXT,
    notes TEXT,
    created_at TEXT NOT NULL
);
ALTER TABLE orders ADD COLUMN customer_id INTEGER REFERENCES customers(id);
```

Миграция (`_migrate_customers_v1`, по образцу существующей
`_migrate_pricing_v2`, флаг в `settings`):
1. Группирует существующие заказы по паре `(client, contact)` (без учёта
   регистра/пробелов), создаёт по одному клиенту на группу.
2. Проставляет `customer_id` у всех заказов в группе.

Поля `client`/`contact` в заказе остаются как есть (используются ботом при
создании заказа, дублируют актуальные данные клиента на момент заказа —
это нормально для истории). При сохранении заказа (из бота или из
приложения) `customer_id` определяется/создаётся автоматически по
контакту, с возможностью вручную сменить привязку в приложении.

Новые функции в `db.py`:
- `find_or_create_customer(name, contact) -> int`
- `get_customer(customer_id)`
- `list_customers(search: str = "") -> [...]` (с агрегатами: число заказов,
  сумма оплаченного, сумма долга — через `LEFT JOIN orders`)
- `update_customer(customer_id, **fields)`

## Экраны приложения

1. **Заказы** — список с теми же фильтрами, что в боте (активные /
   неоплаченные / завершённые / все) + поиск, карточка заказа с полным
   редактированием всех полей, статуса, оплаты, списком вложений
   (добавить/скачать/удалить), заметками.
2. **Новый заказ** — форма (аналог пошагового чата бота, но не требует
   Telegram): выбор/создание клиента, материал, цвет, вес, часы, кол-во,
   срок, прикрепление файлов прямо при создании; цена считается той же
   функцией `calc_price`, что и в боте, с возможностью переопределить вручную.
3. **Клиенты** — список с поиском (имя/контакт), карточка клиента:
   контакты, заметки, история всех его заказов, суммы (оплачено/долг).
4. **Цены и настройки** — форма для `materials` (цена за кг по каждому
   материалу, добавление/удаление), `hour_rate`, `reverse_price`,
   `currency` — то, что сейчас правится командами `/setprice`, `/sethour`,
   `/setmin`, `/delmaterial`. Сохранение — через существующие
   `db.set_setting` / новые функции над `materials`.
5. **Статистика** — переиспользует `db.stats()`: выручка, прибыль, долги,
   расход материала, заказы за месяц — в виде дашборда с карточками/графиком
   вместо текстового сообщения бота.

## Вложения заказа

Приложение — самостоятельный инструмент, не зависящий от Telegram: заказ
можно полностью создать и вести прямо в приложении, включая прикрепление
файлов (фото модели, STL, референсы), без единого сообщения в Telegram.
При этом файлы, пришедшие через бота, тоже доступны.

Одного поля `orders.file_id` для этого недостаточно (нужно несколько
файлов на заказ и два источника — Telegram и локальная загрузка), поэтому
добавляем таблицу:

```sql
CREATE TABLE attachments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id INTEGER NOT NULL REFERENCES orders(id),
    source TEXT NOT NULL,       -- 'telegram' | 'local'
    file_id TEXT,                -- заполнено, если source = 'telegram'
    local_path TEXT,             -- заполнено, если source = 'local'
    filename TEXT,
    file_type TEXT,              -- 'photo' | 'document'
    added_at TEXT NOT NULL
);
```

Существующие `orders.file_id`/`orders.file_type` остаются как есть (не
трогаем схему заказа) — миграция один раз переносит их в `attachments` как
запись с `source = 'telegram'`, если поле было заполнено.

- **Из Telegram**: по клику «Скачать» на вложении с `source = 'telegram'`
  приложение читает `BOT_TOKEN` из общего `.env` и делает прямой HTTP-запрос
  к Bot API (`getFile` → скачивание по полученному пути) через `httpx`, без
  aiogram. Скачанный файл кэшируется на диск (`app/files_cache/<file_id>`).
- **Локальная загрузка**: в карточке заказа кнопка «Добавить файл» открывает
  системный диалог выбора файла (`Flet FilePicker`), файл копируется в
  `app/files_storage/<order_id>/<filename>`, создаётся запись в
  `attachments` с `source = 'local'` и `local_path`.

В обоих случаях вложения одного заказа отображаются единым списком в
карточке заказа, с кнопкой открыть/скачать/удалить на каждом.

## Live-обновление

Фоновый поток в приложении раз в ~3 секунды выполняет лёгкий запрос
(`SELECT MAX(id), (SELECT COUNT(*) FROM orders WHERE ...)` или хэш последних
изменений) и обновляет экран только если что-то реально поменялось —
избегаем лишних перерисовок и нагрузки на UI-поток Flet.

## Обработка ошибок

- Кратковременная блокировка БД записью бота → WAL делает это редким;
  на всякий случай короткий retry (2-3 попытки с паузой в несколько мс)
  вокруг записи из приложения.
- Нет сети / бот API не отвечает при скачивании файла → снек-бар с понятной
  ошибкой, не блокирует остальной UI.
- `.env` без `BOT_TOKEN` → в разделе файла заказа показывается подсказка
  настроить токен вместо ошибки; остальные экраны работают как обычно.

## Тестирование

- Юнит-тесты (pytest) на новые функции `db.py`: customers CRUD, миграция
  группировки клиентов, `find_or_create_customer` — на временной SQLite-базе
  (аналогично тому, как можно тестировать существующие функции `db.py`,
  сейчас тестов нет, но добавляем инфраструктуру `tests/` с fixture на
  временный файл БД).
- Ручная проверка перед сдачей: одновременный запуск бота и приложения,
  создание заказа через Telegram → появление в приложении в течение ~3 сек
  без перезапуска; правка цены материала в приложении → бот использует
  новую цену на следующем расчёте (`/calc` или новый заказ).

## Дистрибуция

`flet pack app/main.py --name "Mochi Desktop"` → один `.exe`. Добавляем
`start_app.bat` рядом с существующим `start.bat`, который при первом
запуске создаёт `.venv`, ставит зависимости (`requirements.txt` пополняется
`flet`, `httpx`) и либо запускает `python app/main.py` в режиме разработки,
либо (после сборки) просто открывает готовый `.exe`.

## Вне рамок (не делаем сейчас)

- Синхронизация в реальном времени с уведомлениями (push) — только polling.
- Мульти-пользовательский доступ по сети — приложение работает на одном ПК.
- Redesign бизнес-логики расчёта цены — переиспользуем как есть.
